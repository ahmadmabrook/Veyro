## Decision
Marking: **[SRC]** means mandated by the cited source paragraph. **[INFERENCE]** means an engineering reading extending a source paragraph; flagged so review can challenge it. **[PROPOSAL]** means a concrete engineering choice proposed here with rationale; it is not an owner business-policy decision. ### D1. Roles and ownership (TSD ¶743, ¶1208, ¶1240)
1. [SRC] DDL and migrations run as a non-runtime owner role. Runtime roles do not own tenant tables (TSD ¶743).
2. [SRC] TSD ¶743 states the flags for `veyro_app` and worker roles: LOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS. [INFERENCE] Extending these flags to the control-plane runtime and worker roles is an engineering inference; TSD ¶743 names the product-plane roles, and ¶1208/¶1969 require only a runtime role "separate from product plane". Control-plane roles are separate from the product-plane `veyro_app` role.
3. [PROPOSAL] Names: **privileged bootstrap owner `veyro_cp_bootstrap`** (see below); tenant-table migration owner `veyro_cp_migrator` (LOGIN only for the tenant-migration job, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLS, owns tenant tables, never used at runtime); runtime `veyro_cp_app`; worker `veyro_cp_worker`; platform-scope owner `veyro_cp_platform` (NOLOGIN, NOSUPERUSER, NOBYPASSRLS, NOCREATEDB, NOCREATEROLE; see D6). Rationale: the sources do not name control-plane roles. The exact privilege matrix is in D6.2.
   **Bootstrap owner [PROPOSAL].** `veyro_cp_bootstrap` is the only role that creates roles, creates schemas and performs platform DDL. A `NOCREATEROLE` migrator cannot grant itself membership in `veyro_cp_platform` (it holds no ADMIN option on it), so no design in this ADR depends on such a grant. In the S1 local test container `veyro_cp_bootstrap` is the container's superuser (synthetic data only). It is used by a separate bootstrap/platform migration job, never by the application, the worker, the tenant-migration job or tests other than the privileged harness (D6.6). It has no runtime use and no steady-state membership. A superuser is not technically confined, so the confinement is by process: bootstrap/platform SQL lives in its own reviewed path, the D5 lint admits only role, schema, grant, platform-table and platform-function DDL in that track (no tenant-table DDL, no DML on tenant tables) and rejects them elsewhere. A superuser created role gets no automatic ADMIN membership (PostgreSQL 16+ adds one only when a non-superuser CREATEROLE role is the creator), which is why the creator is the superuser and the D5 membership check can require zero rows. Any non-local bootstrap identity (managed cloud, a non-superuser CREATEROLE substitute) is a different design with different membership consequences, is out of S1 and stays OPEN (spend is owner-reserved).
4. [SRC] The control plane is a separate database from the product plane: "Control-plane PostgreSQL database; module-prefixed tables; separate runtime role from product plane" (¶1208; ¶1969). [PROPOSAL] Local container for tests, no managed cloud, and product-plane roles hold no grants there.

### D2. Tables and RLS (TSD ¶744, ¶753, ¶1236, ¶1239)
Tenant-owned tables have mandatory FORCE RLS, runtime roles are NOBYPASSRLS, and runtime roles hold no direct cross-tenant grants. These apply to tenant tables only; platform_scope tables are governed by the function-only boundary proposed in D6 (no RLS on them, by recorded choice).
1. [SRC] Every tenant-owned table has `tenant_id UUID NOT NULL`, `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`, and no grant to PUBLIC. Tenant tables keep FORCE RLS without exception.
2. [PROPOSAL] Module-prefixed tables `plt01_*` for Organization, LegalEntity, Brand, Region, Location, Department, CostCenter, TenantConfiguration, lifecycle history, outbox. Tenant registry and placement are platform_scope (D6).
3. [SRC] Tenant-leading indexes for primary list/detail paths; external/provider identifiers unique per tenant/provider; aggregate version supports optimistic concurrency (¶1239). [PROPOSAL] Composite unique `(tenant_id, id)`, composite foreign keys `(tenant_id, parent_id)` so a row cannot reference another tenant's parent, and `version bigint NOT NULL` checked by `WHERE version = :expected`.
4. [PROPOSAL] Lifecycle history tables are append-only (no UPDATE/DELETE/TRUNCATE grant to runtime roles), supporting R07 history without rewrite.

### D3. Policies fail closed (TSD ¶745)
[SRC] Policies compare `tenant_id` to a transaction-local value and fail closed on missing/invalid context. [PROPOSAL] One policy per tenant table `TO veyro_cp_app, veyro_cp_worker` with both `USING` and `WITH CHECK`:
`tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid`

Fail-closed contract: missing or empty context yields zero rows (the comparison is NULL). Invalid context may raise a cast error **or** yield zero rows, depending on whether and when the planner evaluates the expression (for example an empty table may never evaluate it). The ADR does not promise that an invalid UUID always raises. The invariant is: **missing or invalid context may error or return zero rows, and never returns unrestricted rows.** Tests assert "error or zero rows", never a specific error. No tenant-table policy uses `OR true`, a role-membership bypass or a function that can return unrestricted access.

**Trust statement.** The RLS policy trusts the integrity of the `app.tenant_id` setting. The database does not authenticate who set it. Therefore the context-setting primitive (D4) and deny-by-default grants (no PUBLIC, no TRUNCATE/REFERENCES, no owner membership, no unreviewed SECURITY DEFINER, D5) are part of the trusted boundary, not merely application hygiene.

### D4. Transaction-local context and pooling (TSD ¶746, ¶1950)
1. [SRC] Every request or worker command opens an explicit transaction, sets `app.tenant_id`, `app.actor_id` and `app.correlation_id` transaction-locally (`SET LOCAL`), then runs all tenant SQL. Session-level SET is forbidden with pooled connections (TSD ¶746).
2. **PostgreSQL does not prohibit a runtime role from running `SET app.tenant_id = ...`**: a custom GUC with a dotted name is user-settable by any role. This ADR does not claim the database rejects session-level SET. The ban is enforced by (a) a source scan and lint rejecting session-level `SET app.`, `SET SESSION`, `ALTER ROLE/DATABASE ... SET app.` and `set_config(..., false)`, with no exception; (b) the single approved tenancy primitive being the only code path that sets the context, and refusing autocommit and non-UUID values; (c) pool reset on check-in (`RESET ALL`/`DISCARD ALL`) as defence in depth, never the primary control. Reset restores role- and database-level defaults, not an empty state, so a default configured through `ALTER ROLE/DATABASE ... SET app.*` would be re-applied by the reset; the D5 catalog checks therefore require `pg_db_role_setting` to hold no `app.*` entry for any role or database; and (d) reuse tests proving that a deliberately leaked session-level value does not authorize the next transaction (D9). [PROPOSAL] The primitive sets context with `set_config(name, value, true)` (the parameterized form of `SET LOCAL`).
3. [PROPOSAL] Driver and pool: psycopg 3 with psycopg_pool; PostgreSQL 17 (pinned by image digest at implementation review); hash-locked requirements. Alternatives (asyncpg, SQLAlchemy-only) are open at review. EIP ¶754 requires a reviewed capability manifest and supply-chain evidence for psycopg, PostgreSQL and any third-party capability before activation; this proposal is not that manifest. The bounded manifest and supply-chain evidence requirements are in D11.

### D5. Migration lint and review (TSD ¶747)
[SRC] A migration fails if a new tenant table lacks `tenant_id`, FORCE RLS, a policy, expected tenant-leading indexes or runtime-role negative tests, and the lint rejects SECURITY DEFINER functions unless explicitly reviewed. [PROPOSAL] Plain ordered SQL migrations applied by `veyro_cp_migrator`; a Python lint over the SQL plus live catalog assertions; a mutation corpus with one failing migration per rule. The lint and catalog assertions must also fail on:
- any TRUNCATE or REFERENCES grant to runtime roles (TRUNCATE ignores RLS);
- any `pg_default_acl` entry that grants to PUBLIC or to a runtime role (an entry that only revokes, such as `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`, is the safe pattern and is allowed); and PUBLIC privileges on schemas, tables, sequences and functions (including the default PUBLIC EXECUTE on new functions);
- PUBLIC holding CONNECT or TEMPORARY on the control-plane database (`datacl`; bootstrap runs `REVOKE CONNECT, TEMPORARY ON DATABASE ... FROM PUBLIC`, then grants CONNECT only to the named login roles), and any product-plane role holding CONNECT there;
- views that are not `security_invoker = true`, or any view over a tenant table unless on an explicit reviewed allowlist (banned by default);
- `pg_auth_members` showing a runtime role (`veyro_cp_app`, `veyro_cp_worker`) as a member, directly, transitively through inheritance or through a SET path, of `veyro_cp_migrator`, `veyro_cp_platform`, a table owner or any role that owns tenant or platform_scope objects (so `SET ROLE` to any of them cannot succeed); and zero `pg_auth_members` rows with `roleid = veyro_cp_platform` at all, in every state, counting ADMIN, INHERIT and SET edges and including the runtime roles, the migrator and the bootstrap owner (no time window in which a membership is granted and revoked exists in this design; D6.1);
- `pg_db_role_setting` containing any `app.*` default (for example `app.tenant_id`, `app.actor_id`, `app.correlation_id`) for any role or database, because `RESET ALL`/`DISCARD ALL` restores such defaults and would re-apply them on the next pooled checkout;
- role flags (`pg_roles`), `pg_class.relforcerowsecurity`, ownership, and `pg_proc.prosecdef`.

The lint also enforces the two migration tracks (D6.1): tenant migrations (run as `veyro_cp_migrator`) may not touch `plt01_platform` or `plt01_api` objects except the permitted `REFERENCES` foreign key to `plt01_platform.tenants`; bootstrap/platform migrations (run by `veyro_cp_bootstrap`) may not create or alter `plt01` tenant tables.

SECURITY DEFINER exceptions require explicit review and an allowlist entry naming the function, owner role, pinned `search_path`, EXECUTE grantees and a review ID. An unlisted SECURITY DEFINER function fails lint.

### D6. platform_scope isolation (TSD ¶753, ¶783, ¶1243) — ACCEPTED engineering decision (acceptance candidate, see header); D6-a and D6-b closed as engineering choices
[SRC] TSD ¶753 lists "explicit platform_scope tables" as a distinct item from tenant-owned tables. Cross-tenant reporting is prohibited in product-plane data paths (TSD ¶783). Support/break-glass access creates delegated actor evidence (¶1243). No source prescribes RLS or no-RLS for platform_scope; this is an engineering choice, not owner-reserved. It is decided here as an engineering choice within the narrow acceptance scope in the header.

**D6-a / D6-b decision [PROPOSAL]: function-only schema/grant boundary; no RLS on platform_scope tables; no policy of any kind for `veyro_cp_platform`.**

Comparison:
| Option | What it adds | Cost / risk |
|---|---|---|
| A. FORCE RLS on platform_scope with a policy for `veyro_cp_platform` | A catalog-visible flag on every table | `veyro_cp_platform` is NOBYPASSRLS, so FORCE RLS with no policy returns no rows. Making it work needs a policy that lets the function owner see rows. `USING (true)` is permissive and decorative: only the owner reaches the table (the grant boundary already decides that), so it adds no enforcement. A non-decorative policy would key on a GUC set by the same function, which is the same trust as the function body, plus a cross-tenant list path that looks like a tenant policy and invites copy-paste of `OR true`. Lint must then special-case "FORCE RLS plus a permissive policy" as acceptable, weakening the rule that no permissive policy exists. |
| B. Function-only boundary (chosen) | Tables unreachable by any runtime role; every access goes through a closed, reviewed function allowlist | Correctness rests on grants, ownership, function bodies and the catalog checks. These are all lint-asserted (D5, D9). A future cross-tenant Console read needs its own reviewed function; it cannot be added by a grant. |

Choice B: it keeps the invariant "no permissive policy anywhere" mechanically true, keeps FORCE RLS meaning "tenant table" in lint (every table outside `plt01_platform` must be FORCE RLS; every table inside it must be on the platform_scope allowlist, have no policy, hold no runtime grant and have `relrowsecurity = false`), and avoids a policy that only looks like protection. The residual risk (a mistaken grant or function body) is covered by the catalog assertions and failure tests below, not by RLS. Changing this to option A later needs an ADR change.

**D6.1 Schemas, ownership and migration tracks [PROPOSAL].** Executable sequence, all in the S1 local container:
1. `veyro_cp_bootstrap` (D1.3, superuser) creates the roles `veyro_cp_migrator`, `veyro_cp_platform`, `veyro_cp_app`, `veyro_cp_worker` with the flags in D6.2, revokes CONNECT/TEMPORARY on the database from PUBLIC and grants CONNECT only to the login roles, revokes CREATE on `public` from PUBLIC, and creates the schemas. No `GRANT <role> TO <role>` statement appears anywhere, so no membership edge exists in any state.
2. Tenant tables: schema `plt01`, schema and tables owned by `veyro_cp_migrator`, FORCE RLS. Created by the **tenant track**, run as `veyro_cp_migrator`.
3. Platform tables (`tenants` registry, `tenant_placement`): schema `plt01_platform`, schema and tables owned by `veyro_cp_platform`. API functions: schema `plt01_api` **owned by `veyro_cp_platform`** (the schema owner therefore holds CREATE on it by ownership), functions created and owned by `veyro_cp_platform`. These are created by the **platform track**: `veyro_cp_bootstrap` runs the platform DDL either as the owner directly (`SET ROLE veyro_cp_platform`, which a superuser may do) or with `ALTER ... OWNER TO veyro_cp_platform`; no non-superuser role needs membership in `veyro_cp_platform`, and `veyro_cp_platform` needs no further CREATE grant because it owns `plt01_api` and `plt01_platform`. The migrator has no privilege in `plt01_api`.
4. Schema USAGE and the foreign key, concrete: the runtime roles get no USAGE on `plt01_platform`, so it is not name-resolvable to them. Tenant tables carry `FOREIGN KEY (tenant_id) REFERENCES plt01_platform.tenants (tenant_id)`. Declaring it needs, for `veyro_cp_migrator`, **USAGE on schema `plt01_platform`** and **REFERENCES on `plt01_platform.tenants (tenant_id)`**, both granted by the owner `veyro_cp_platform` (applied by bootstrap). These are the only privileges the migrator holds in `plt01_platform`; they are steady-state grants, not role memberships, and the D5 check lists them as the single allowed exception. The runtime roles hold no REFERENCES grant. PostgreSQL runs referential-integrity checks as the owner of the referenced table (here `veyro_cp_platform`, whose inherent owner privileges on `tenants` are deliberately not revoked) and bypasses RLS for them, so inserting a tenant row as `veyro_cp_app` is expected to need no runtime grant on `tenants`. **This is a review finding to be tested, not an assumption** (D6.6 tests 16-17): the test inserts a tenant-table row as `veyro_cp_app` with a registered tenant id (must succeed) and an unregistered one (must fail with a foreign-key violation), with no grant on `tenants` to `veyro_cp_app`. If the test fails on the target PostgreSQL version, the FK is dropped and the provisioning function owns existence (previous fallback).
5. **Who may alter platform tables in later migrations:** only the platform track, run by `veyro_cp_bootstrap`, in its own reviewed path with an independent review per change. `veyro_cp_migrator` cannot ALTER, DROP or CREATE in `plt01_platform` or `plt01_api` (it owns nothing there; the only grants are item 4) and cannot `SET ROLE veyro_cp_platform`. The two tracks are separate ordered migration sets, and the D5 lint rejects a file in the wrong track.

**D6.3 Function allowlist for S1 [PROPOSAL].** Closed list; adding an entry needs an ADR change and a review ID.
1. `plt01_api.provision_tenant(p_external_key text, p_idempotency_key uuid, p_actor_id uuid, p_correlation_id uuid) RETURNS TABLE (tenant_id uuid, replayed boolean)`. Inserts the `tenants` registry row (state PROVISIONING, placement `UNASSIGNED`, no region, no key reference, because region and key values are owner-reserved) with a database-generated `tenant_id`. `p_actor_id` and `p_correlation_id` are caller claims; with no access log in S1 they are validated as non-null UUIDs and are not part of the idempotency payload. EXECUTE: `veyro_cp_app` only. Idempotency contract:
   - **Payload** is `p_external_key`. The registry has a unique constraint on `idempotency_key` and a unique constraint on `external_key`.
   - **First call:** `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING`; a row returned means `replayed = false`.
   - **Replay (same key, same payload):** no row returned by the insert, the function reads the existing row, compares `external_key`, and returns the existing `tenant_id` with `replayed = true`. The caller must **skip all tenant-side writes** (provisioning step 3 below) when `replayed` is true.
   - **Same idempotency key, different payload:** the function raises a dedicated, documented error (a reserved SQLSTATE chosen at review) and writes nothing. A different idempotency key with an already-registered `external_key` raises the same error (unique violation mapped to it); neither case returns a `tenant_id`.
   - **Concurrency:** two concurrent calls with the same key serialize on the unique index; the second waits for the first transaction to end, then either sees its committed row (replay) or, if the first rolled back, inserts. The function requires READ COMMITTED (a stricter isolation level that raises a serialization failure is a retryable error, never a duplicate). Exactly one registry row per key is a tested invariant (D6.6).
   - **Atomicity and rollback:** the registry row and all tenant-side rows are written in one transaction (provisioning section). Therefore `replayed = true` implies the earlier committed transaction also wrote the tenant-side rows; a failure at any step rolls back both and a retry is a fresh first call. An unknown-outcome commit (network failure, NET) is resolved by retrying with the same key.
2. `plt01_api.resolve_placement(p_tenant_id uuid) RETURNS` one typed row `(tenant_id, lifecycle_state, region_ref, cluster_ref, relocation_state, relocation_epoch, key_ref, contract_version)`; unknown tenant returns no row (never a default placement). EXECUTE: `veyro_cp_app`, `veyro_cp_worker`. The returned row is the **internal** shape. What may leave the control-plane process is narrower, see D6.7.
No access-log helper exists in S1. No archive, delete, relocate-source-deletion or cross-tenant list function exists in S1 and lint rejects any such entry (see the audit statement below). S1 operations are nondestructive synthetic-fixture operations only; no support or break-glass function exists. Each function is SECURITY DEFINER with `SET search_path = pg_catalog, plt01_platform, pg_temp`, schema-qualified references, typed parameters, no dynamic SQL, `REVOKE EXECUTE ... FROM PUBLIC`, and a D5 allowlist entry (function, owner, pinned search_path, EXECUTE grantees, review ID).

**D6.4 Transaction behaviour and the conditional access-log seam [PROPOSAL].** **S1 default: no interim access log** (OWNER-Q1 has no affirmative decision; the seam is not authorized). In S1 each allowlisted function runs in the caller's transaction, a failure rolls the whole transaction back, and the only platform-side record of an effect is the registry row itself. This is **not a waiver of MOD-008 audit**: no audit is claimed, and S1 has no destructive, support or break-glass operation, only nondestructive synthetic-fixture operations.

*Conditional seam, built only after an affirmative OWNER-Q1 = Yes (not designed into S1):* a table `plt01_platform.access_log` owned by a **separate NOLOGIN role `veyro_cp_logowner`** that has no members, no LOGIN, owns only that table and holds no other privilege. `veyro_cp_platform` is granted INSERT and SELECT only on it, and a helper `plt01_platform.write_access_log(...)`, owned by `veyro_cp_platform` and not executable by any runtime role, is called by each function in the same transaction as the effect. Columns: `occurred_at` (`transaction_timestamp()`), function name, `session_user` (the real login role), tenant_id, claimed `actor_id` and `correlation_id` (caller claims, not authenticated identity), outcome. Honest limits, with no absolute immutability claim: (a) a table owner holds inherent powers (it can re-grant itself privileges, ALTER, DROP, disable triggers), so revoking grants on a self-owned table does not make it append-only; the separate owner is what denies those powers to `veyro_cp_platform`, and the owner is only unreachable by roles without membership, not by a superuser, the bootstrap owner, a restore or filesystem access; (b) a failed or denied call rolls back with its transaction, so the log records committed effects only; (c) the log is not audit evidence (interim-log statement below). Added checks if built: `pg_class.relowner` of `access_log` is `veyro_cp_logowner`, `pg_auth_members` has no row with `roleid` or `member` = `veyro_cp_logowner`, and the denial tests in D6.6 (11) run through the privileged harness.

**D6.5 SET ROLE / membership protections [PROPOSAL].** Runtime roles are members of no role (not even through INHERIT, SET or admin options), so `SET ROLE` to the migrator, platform or any owner fails; `session_user` cannot be changed by a non-superuser. No `ALTER ROLE/DATABASE ... SET role` or `app.*` default. `REVOKE CREATE ON SCHEMA public FROM PUBLIC` and no object in `public`. The catalog checks in D5 assert every item in this paragraph.

**D6.6 Failure tests [PROPOSAL; obligations, not evidence].** Each must fail the check or the call: (1) `veyro_cp_app` SELECT/INSERT/UPDATE/DELETE on any `plt01_platform` table; (2) USAGE on `plt01_platform` held by a runtime role; (3) EXECUTE on any non-allowlisted function by a runtime role (and, only if the conditional log is built, on `write_access_log`); (4) a runtime role member of `veyro_cp_platform`, directly, via an intermediate INHERIT role, or via SET; (5) `SET ROLE veyro_cp_platform` or `veyro_cp_migrator` by `veyro_cp_app`; (6) any `plt01_platform` table with a policy or `relrowsecurity = true`, or any `plt01` table without FORCE RLS; (7) a SECURITY DEFINER function missing a pinned `search_path` or with `pg_temp` before `pg_catalog`, or with PUBLIC EXECUTE; (8) an object in `plt01_platform` with a PUBLIC ACL entry; (9) a function raising after its insert leaves no registry row; (10) a `search_path` hijack attempt (a same-named object in `public` or `pg_temp`) does not change function behavior; (11) **only if the conditional log is built (D6.4):** through the **privileged harness**, UPDATE, DELETE, TRUNCATE, ALTER TABLE, DROP TABLE, GRANT and trigger disabling on `access_log` are denied to `veyro_cp_platform` (`veyro_cp_platform` is NOLOGIN with no members, so it cannot be tested by connecting as it; the harness connects as the container superuser and runs `SET ROLE veyro_cp_platform`, which asserts denial for that role only and makes no claim about the superuser or `veyro_cp_logowner`); (12) a retry with the same idempotency key and payload returns the same `tenant_id` with `replayed = true` and creates no second registry row; (13) the same key with a different `p_external_key` raises the documented error and changes nothing; (14) concurrent calls with the same key (at least two connections racing) yield exactly one registry row and one `replayed = false`; (15) on `replayed = true`, the tenant-side step is skipped and no second lifecycle-history or `tenant.provisioned` outbox row exists; a failure in the tenant-side step rolls back the registry row so the retry is a first call; (16) with no grant on `plt01_platform.tenants` to `veyro_cp_app`, an insert into a tenant table with a registered `tenant_id` succeeds; (17) the same insert with an unregistered `tenant_id` fails with a foreign-key violation (together, 16-17 test the PostgreSQL RI ownership semantics in D6.1 item 4); (18) the catalog shows zero `pg_auth_members` rows for `veyro_cp_platform`, the function owner is `veyro_cp_platform`, and `veyro_cp_platform` holds CREATE on `plt01_api` (by ownership); (19) `veyro_cp_migrator` cannot ALTER or DROP a `plt01_platform` table, create a function in `plt01_api` or `SET ROLE veyro_cp_platform`; (20) `datacl` shows no PUBLIC CONNECT/TEMPORARY and a product-plane login role cannot connect; (21) for `resolve_placement` through the D6.7 contract, an unknown tenant id and an `UNASSIGNED` tenant produce byte-identical external responses, and `key_ref` is absent unless D6.7 allows it.

**D6.7 Product-plane placement interface [PROPOSAL; transport OPEN].** Stable contract `placement.resolve.v1`: input `tenant_id`; output exactly the `resolve_placement` row above; read-only; versioned by `contract_version`; fail closed (unknown tenant, `UNASSIGNED` placement or a relocation state that forbids routing returns an explicit non-routable result, never a default cluster, region or credential); responses carry `relocation_epoch`, and consumers must reject or re-resolve commands carrying an older epoch (TSD ¶778). The product plane receives no database grant, schema, role or credential in the control-plane database (D1.4). Control-plane service code implements the contract by calling `resolve_placement` as `veyro_cp_app` or `veyro_cp_worker`. **Exposure and binding rules [PROPOSAL]:** (1) in S1 the contract is **test-harness only**; it is not exposed outside the control-plane process (no network listener, no library handed to the product plane) until a verified caller-to-tenant binding and an auth/transport design exist and have been reviewed, because the function accepts any caller-supplied `tenant_id` and would otherwise be a tenant-existence and placement oracle; (2) an external response for an unknown tenant is identical to the response for a non-routable one (`UNASSIGNED` or a forbidding relocation state): the same non-routable result with no distinguishing field, status or timing-relevant extra work that the design controls; (3) the external response includes `key_ref` only if the credential issuer requires it, otherwise it carries the minimum routing fields; the internal row above is not the external shape. **Deferred, OPEN:** transport (in-process library vs network service), caller authentication and authorization (depends on MOD-007/008), caching and invalidation, rate limits, how the product plane obtains credentials after resolution, and versioning policy. None of these may be satisfied by granting the product plane table, schema or function access.

**D6.8 Support/break-glass.** Delegated actor evidence (¶1243) belongs to MOD-008 audit; break-glass authorization and approvals depend on MOD-007/008 and are OPEN. No support or break-glass function exists in S1 and none may be added without the MOD-008 audit or an `OWNER-*`/governance decision.

**Provisioning: who invokes `ProvisionTenant` and how one transaction writes both planes [PROPOSAL].** The invoker is the MOD-004 control-plane command service running as `veyro_cp_app`; the human or system caller's authentication and permission check (¶1237 "declares permission") belong to MOD-007/008 and are deferred. In S1 the only caller is the test harness with synthetic actors. One explicit transaction: (1) `veyro_cp_app` calls `plt01_api.provision_tenant(...)`, which as `veyro_cp_platform` inserts the registry row and returns `(tenant_id, replayed)`; (2) the tenancy primitive sets `app.tenant_id` transaction-locally to that value; (3) only if `replayed` is false, `veyro_cp_app` inserts the tenant rows (lifecycle history, outbox, any initial hierarchy) under FORCE RLS; on a replay step 3 is skipped entirely (D6.3 idempotency contract); (4) commit. No role holds both grant sets: `veyro_cp_app` has only EXECUTE on the function plus tenant-table DML, and `veyro_cp_platform` has no tenant-table privilege. A failure in step 3 rolls back step 1 and 2 together, so no registry row exists without its tenant rows. Residual trust: step 2 relies on the primitive (D3 trust statement); a compromised `veyro_cp_app` could set another tenant's id, which is why the primitive and the D5 and D6.6 checks are part of the trusted boundary. Initial placement stays `UNASSIGNED` until an owner-reserved region decision exists, so provisioning needs no region or key policy.

**Interim access log is NOT the MOD-008 immutable audit, and is absent from S1 by default.** If it is ever built (D6.4, conditional seam), the platform access log is an engineering record of committed function effects. It is not the immutable audit and approvals required by ¶1231 and INV-PLT-01, it is not claimed immutable or append-only beyond the specific denials tested for `veyro_cp_platform`, it records caller-supplied actor claims, and it cannot satisfy any destructive-action gate (approvals, retention checks, immutable audit record) or Appendix I conformance for INV-PLT-01. Consequence: no archive, delete, hard-delete, relocation-source-deletion or other destructive lifecycle command may be built, enabled or accepted on this log; those stay blocked until MOD-008 immutable audit exists or an `OWNER-*` or governance decision says otherwise, and the allowlist lint (D6.3) enforces this. Whether the log may exist inside MOD-004 at all is a cross-module seam question (OWNER-Q1 in the module spec). **Omitting the log is not a waiver of MOD-008 audit and does not block S1.** OWNER-Q1 is pending and is needed only to add the seam; no Yes decision has been supplied.

### D12. Gate order and code timing — accepted no-code-before-Ready gate [INFERENCE]
**Authoritative rule.** EIP §8: Ready requires "Dependencies satisfy the permitted §18 dependency state; scope/requirements/screens identified; module spec drafted; environment/tool access available" (EIP ¶749-750). The Capability gate requires an Active module to have a reviewed ACTIVE manifest and bars use of any unreviewed capability for implementation (EIP ¶753-754). Scenario Review precedes Implementation Complete (EIP ¶755-758). The unlock rule keeps the next module LOCKED until the active module is APPROVED, and permits research, documentation or environment preparation only if it cannot create production implementation that bypasses the gate (EIP ¶773). A written spec alone does not make a module Ready.

**Position.**
1. Stdlib-only design work (this ADR, the module spec, the scenario catalog, mutation-corpus designs as text) is legal now: it is documentation and creates no production implementation.
2. Stdlib-only code or SQL committed to the S1 paths (`backend/app/tenancy/`, `backend/migrations/`, `infra/db/`, `backend/tests/integration/tenancy/`) is production implementation of this module. - Epoch rule: responses and events carry `relocation_epoch`; consumers reject or re-resolve a command or message with an older epoch (TSD ¶778, D6.7).
- Transport, caller authentication and authorization between the product plane (MOD-066) and the control plane are **OPEN** and follow D6.7: no product-plane database access, schema or function grant; until a verified caller-to-tenant binding and auth/transport design are reviewed, the contract is test-harness only and is not exposed outside the control-plane process.
- Failure behavior: a missing appearance returns an explicit "not set / defaults" result, never another tenant's or brand's value.
- WHT-01 V2 features (CMS, app builder, build/store release, remaining brand tokens) are untouched. If WHT-01 later needs `accent_color`/`logo_asset_ref`, it may read this contract as V1 history and does not write PLT-01 tables. If WHT-01 owns logo or color in V2, who writes them is the OPEN handoff in D15.2.3.

**D15.9 Error states (PROPOSED codes; mapped to API status at API design, OPEN).** `UNAUTHENTICATED` and `FORBIDDEN` (MOD-007/008, dependency unavailable means fail closed); `TENANT_CONTEXT_INVALID` (missing/invalid context never returns data, D3); `BRAND_NOT_FOUND` (also for another tenant's brand); `TENANT_NOT_WRITABLE` (lifecycle state forbids writes, state names OPEN with R01); `VERSION_CONFLICT` (`expected_version` mismatch, returns current version); `IDEMPOTENCY_CONFLICT` (same key, different payload; writes nothing); `VALIDATION_FAILED` (field-level: malformed color, guardrail violation, unknown field, executable or URL content); `ASSET_REF_UNVERIFIED` (logo reference unknown to the tenant's storage scope); `RELOCATION_EPOCH_STALE`; `DEPENDENCY_UNAVAILABLE` (audit or authorization unavailable, no write). Errors never include another tenant's data.
Idempotency (PROPOSED, mirrors D6.3 for a tenant-side command; the D6.3 platform function is unchanged):
- **Store.** Tenant table `plt01_command_idempotency` (tenant track, D6.1): `tenant_id UUID NOT NULL`, `command text`, `idempotency_key uuid`, `payload_hash bytea` (hash over `brand_id`, `accent_color`, `logo_asset_ref`, `expected_version`; never `tenant_id`, `actor_id`, `correlation_id`), `result_ref` (resulting `version` and the appearance/history identifiers), `created_at`. `PRIMARY KEY (tenant_id, command, idempotency_key)`; `ENABLE` and `FORCE ROW LEVEL SECURITY` with the D3 policy for `veyro_cp_app, veyro_cp_worker`; no PUBLIC grant; `veyro_cp_app` holds SELECT and INSERT only (no UPDATE, DELETE, TRUNCATE), so a stored key cannot be rewritten at runtime. The same key in another tenant is a different row and never visible. Retention and purge of these rows are owner-reserved and OPEN (R07, retention), and the lint must still reject runtime DELETE.
- **Same-transaction atomicity.** The claim row, the `plt01_brand_appearance` write, the history row and the outbox row are written in the one command transaction (D15.4). Any failure rolls back all of them, including the claim, so a retry with the same key is a fresh first call. No effect exists without its claim row and no claim row exists without its effect.
- **Replay-before-version order.** After the tenant context is set: (1) `INSERT INTO plt01_command_idempotency ... ON CONFLICT (tenant_id, command, idempotency_key) DO NOTHING`; (2) if a row was inserted, this call owns the key: continue to the version check and the write; (3) if not, read the stored row: same `payload_hash` returns the stored result with `replayed = true` and **skips the version check and every write** (so a replay after the version has advanced is not a `VERSION_CONFLICT`); a different `payload_hash` returns `IDEMPOTENCY_CONFLICT` and writes nothing. The version check (`WHERE version = :expected`, first set expects 0) runs only for calls that own the key.
- **Concurrency.** Two concurrent calls with the same key serialize on the primary key index: the second waits for the first transaction to end, then either reads the committed claim (replay or `IDEMPOTENCY_CONFLICT`) or, if the first rolled back, inserts and proceeds. The command requires READ COMMITTED; a serialization failure under a stricter level is a retryable error, never a second effect. Exactly one effect per key is a tested invariant.
- **Concurrent first-set conflict.** Two calls with different keys and `expected_version = 0` for the same brand race to create the single row. The create uses `INSERT ... ON CONFLICT (tenant_id, brand_id) DO NOTHING` (or an equivalent catch of the `(tenant_id, brand_id)` unique violation inside the primitive); the loser rolls back its claim, history and outbox rows and returns `VERSION_CONFLICT` with the current version. The raw unique-violation SQLSTATE and constraint name never reach the caller.
- An unknown commit outcome is resolved by retrying with the same key. Exact one effect per key (one appearance change, one history row, one outbox row) is preserved in every path above.

## Rationale
Choosing roles, policy shape and context handling now, in a reviewed ADR, prevents isolation primitives from being invented in code, and keeps engineering choices separate from owner authority. Real PostgreSQL in a local container exercises RLS semantics that mocks cannot. Stating plainly that RLS trusts the context-setting primitive keeps the trusted boundary explicit.

## Alternatives considered
- Shared control/product database with schema separation: rejected as the default, weaker than ¶1208 separation and harder to assert.
- Session-level tenant variable: forbidden by TSD ¶746.
- Application-filter-only isolation: rejected, does not satisfy TSD ¶748.
- Relying on BYPASSRLS or owner connections in workers: forbidden by TSD ¶743.
- Putting platform_scope tables under a permissive tenant-table policy: rejected; it would weaken tenant-table RLS.
- FORCE RLS on platform_scope with a function-owner policy (D6 option A): rejected, adds a decorative or special-cased policy without enforcement beyond the grant boundary.
- A dual-grant provisioning role holding both registry and tenant-table privileges: rejected; the function split in D6 avoids it.
- Building MOD-003-style foundation-only acceptance: not available, ¶1954.
