# Lean execution — all Veyro modules MOD-001 through MOD-074

**Core rule:** Implement the simplest correct solution that satisfies the current module's governing requirements and required assurance. When the mandatory module-exit checklist passes, certify/close immediately and advance. Optimize time to usable product, not artifact, review, test, or task count. This policy does not change the approved Blueprint/TSD/EIP, Development Constitution, security/privacy/data-integrity obligations, model routing, certification, convergence caps, or DC-16 owner stops.

## Scope decision before adding work

Classify each discovered item immediately as `MANDATORY_NOW`, `DEFERRED`, or `OPTIONAL` in the active module's work record. Only `MANDATORY_NOW` may block closure. For a proposed active task, record: (1) exact governing requirement or concrete P0/P1 correctness/security defect, (2) observed failure if omitted now, (3) certification dependency, and (4) whether legal deferral is possible. If no governing requirement or concrete certification dependency exists, do not add it to the active plan; record it as `DEFERRED` with a named future module or backlog owner and reason. `OPTIONAL` means no tracked delivery obligation unless later adopted into a future scope.

Prefer explicit code, small interfaces, bounded domain logic, simple schemas, and minimal dependencies. No generalized framework, generic engine, extra plugin system, speculative extensibility, convenience tooling, broad edge-case hardening, or future integration solely for theoretical completeness. Refactor only when current duplication creates a demonstrated correctness risk, the current requirement demands an abstraction, or multiple **active** requirements already share it.

## Assurance proportional to artifact and risk

- Material executable code/script/validator changes: the minimum **governed** bounded code review. Documentation, ADR, governance-only records, unchanged generated evidence, and deterministic metadata changes do not trigger a code review by themselves; they receive their applicable architecture/spec, data-integrity, deterministic, or Gatekeeper checks. A module-level independent code-review field in the EIP must still be satisfied when the module has executable code; do not invent a code diff or self-waive a governing gate.
- One shared implementation surface → one bounded implementation → one deterministic scenario batch → one legitimate assurance boundary → individual scenario dispositions. A scenario ID is a validation obligation, not a separate implementation job. Never add an assurance round merely for confidence on an unchanged snapshot.
- Local deterministic tools handle tests, lint/format, schema and manifest checks, hashes, scans, indexing, static analysis and status aggregation. Claude is reserved for implementation needing reasoning, architecture decisions, root cause, complex remediation, independent code/security judgment and genuine manual QA. One Claude operation has one primary outcome; no multi-phase prompt.
- At module start classify the module `LOW` (mostly config/docs/simple CRUD), `MEDIUM` (normal domain logic/integration), or `HIGH` (security, money/ledger, tenant isolation, access, offline reconciliation, certification-critical). Tier selects the **minimum appropriate review depth**, never cancels an explicit governing gate. LOW gets no HIGH-style assurance by analogy; MEDIUM gets bounded code/scenario review; HIGH gets the deeper exact risk-specific proofs its requirements demand. Reclassify only with a recorded new risk fact.

## Module exit and operation budget

Each active module has a `MODULE_EXIT_CHECKLIST` of mandatory criteria only: requirement totals/satisfied/blocked, executable changes, deterministic tests, required review/assurance, owner decisions, and remaining bounded operations. Close immediately when all mandatory criteria pass. Do not hold it for polish, optional cleanup/tests, extra confidence, or future-proofing.

At module start record an initial bounded-operation estimate, tier, and timestamp. Track completed operations, operations added after start with a reason and classification, substantive review count, assurance count, and deferred-item count. Preserve historical project counters; a new estimate is not a reset or retry entitlement. If completed operations for the module exceed **150% of the initial estimate**, mark `SCOPE_EXPANSION_ALERT` and perform a documented scope review before further ordinary implementation/review. The review checks every added item against the four scope questions, defers optional work, and re-estimates the remaining mandatory path. It does not waive mandatory work, reset the baseline, or authorize a forbidden assurance round. If an alert occurs mid-operation, preserve/finish or safely interrupt that already-authorized operation, then review scope before dispatching the next one.

The operational record is `control/LEAN_EXECUTION_STATE.json`: each added operation has an ID, `MANDATORY_NOW` classification, governing reason and estimated count; each deferred item has a future owner; each assurance operation has a boundary, outcome and evidence path. A scope review records its evidence path, reviewed completed count and revised mandatory remainder as `scopeReviewedThroughCompleted` plus a `scopeReview` record. The deterministic guard counts completed runner progress events and completed review operations since the module's baseline. Existing historical counts stay in their original ledgers. For MOD-001 only, adoption sets a *remaining-work* baseline while preserving all earlier runner operations; MOD-002 onward establish their initial baselines when unlocked.

The project dashboard shows for each active module: tier, mandatory work remaining, deferred/optional items, executable changes, reviews, assurance and bounded operations remaining, scope expansion %, current critical path, and estimated distance to closure. Program metric `TIME-TO-NEXT-PRODUCT-MILESTONE` states both the named milestone and the best supported distance estimate (bounded operations if no defensible calendar-time model). Unknowns stay `unknown`, not invented zeros.

## OWNER_STOP is the last resort

For MOD-001 through MOD-074, do not enter `OWNER_STOP` merely because the first technical path is blocked. Before a discretionary owner stop, exhaust **legal, safe, already-authorized** alternatives that satisfy the same governing criterion. For hosting, CI, and infrastructure limits, evaluate the simplest applicable existing account/hosting path, disposable branch or PR, temporary repository/mirror, isolated fork, or local deterministic substitute **only if the governing scenario accepts that substitute**. Choose between materially equivalent technical implementations autonomously; do not ask the owner to make a choice with no product, business, cost, security, or governance consequence. If the issue is purely technical, continue solving it.

Record a compact `OWNER_STOP_ASSESSMENT` before stopping: exact blocked criterion and observed failure; each plausible safe alternative and its disposition/evidence; why no already-authorized path remains; and the single minimum owner decision/action needed. A path is not exhausted by assertion alone; use a bounded feasibility probe when safe and relevant. Never claim an unexecuted scenario PASS or reinterpret a governing requirement to avoid a stop. Do not create speculative infrastructure or extra assurance merely to complete the alternatives list.

This last-resort rule **does not relax hard owner stops**. Do not cross into real production deployment, new paid-service activation/spend, real regulated/customer/member data, exposure of secrets, destructive remote actions, force-push/history rewrite, or genuinely unresolved product/business decisions without the required authorization. If such a hard boundary is reached, stop the affected action immediately; assess only safe alternatives on its near side and report the exact decision if none suffice. Existing convergence/review caps and certification gates remain binding.

### Blocked-operation resolution — MOD-001 through MOD-074

No bounded operation may remain generically `BLOCKED`. Record its exact prerequisite, blocker owner, unblock condition, next legal action, and automatic resume trigger. Classify it immediately as `TECHNICAL_BLOCKER` (solve by the simplest authorized path), `DEPENDENCY_BLOCKER` (execute the identified prerequisite operation and resume when its recorded condition passes), `MISSCOPED_WORK` (move the prerequisite to its existing owning operation), or `HARD_OWNER_BOUNDARY` (use `OWNER_STOP` only after the last-resort assessment above). If the operation's own mandatory criteria already pass, close it instead of holding it for unrelated work. Check held operations' resume triggers at each safe operation transition; preserve WIP=1, active healthy work, review caps, evidence, and completed counts. If another dependency-safe operation is legal, continue it while the blocked operation waits. Do not invent a scenario PASS or waive a gate to clear a block.

## Permanent fast module execution — MOD-002 through MOD-074

At each module transition, make one **compact bounded plan** containing only mandatory executable surfaces, shared scenario batches, required reviews, certification, and a bounded operation count. If it initially exceeds 20 operations, compress shared implementation, verification, evidence, and assurance boundaries before execution. Do not create a large planning phase or artifact absent an explicit governing requirement. Start real executable code as soon as the minimum legal boundary is known: **minimum plan → implementation → deterministic verification → mandatory assurance → batch disposition → certification/closure**. MOD-002 prioritizes executable control-plane entities, interfaces, persistence, events/outbox, and required governance mechanisms; MOD-003 prioritizes executable localization, RTL, accessibility, and shared platform foundations; MOD-004 prioritizes actual tenant/organization/brand/location domain code. Subsequent modules follow the same code-first rule.

Every operation has one coherent implementation surface, one clear outcome, and the minimum required evidence. Before adding work ask whether omitting it now would fail mandatory acceptance or certification; otherwise defer or skip it. Batch scenarios, tests, evidence, and qualified reviews when they share a legitimate boundary, while preserving individual scenario dispositions. Sonnet is the normal implementation/test/fix worker; use Opus only for architecture-sensitive or high-risk implementation and the independent review, manual QA, security/performance/resilience, or Gatekeeper roles the governing gate requires. Never add a second opinion or confidence review of unchanged material. Preserve P0/P1, correctness, security, data integrity, explicit certification, convergence caps, and hard owner stops.

**Aggressive bloat and scope check.** Read existing live operation history and the bounded plan before each new dispatch. Trigger `BLOAT_RISK` if whole-operation age exceeds **3×** the rolling recent completed-operation duration, **or** more than eight meaningful dispatches occur without closure, **or** the strategy advances past `v5` without closure. Immediately audit the remaining mandatory criterion, then finish it under a minimum closure path or move unrelated work to an **existing** planned operation. A new bounded operation is permitted only when an explicit mandatory criterion cannot fit a planned one. Do not let WIP=1 become idle waiting when another dependency-safe operation is legal. If the current planned operation count grows beyond **150%** of the module's initial bounded plan, raise `SCOPE_EXPANSION_ALERT` and reconcile mandatory scope before ordinary dispatch; do not reset the baseline or replay completed work.

Progress means a durable reduction in unmet mandatory criteria, blockers, unresolved dependencies, required evidence, scenario batches, or remaining module operations—not agent calls or artifacts alone. Track planned/completed operations, recent completed-operation duration, bloat and loop events, owner stops, and module elapsed execution time from existing control records; diagnose material throughput degradation without building new instrumentation. Optimize **mandatory work completed per hour**. Use the permanent anti-loop and last-resort OWNER_STOP rules already in force. As soon as mandatory exit criteria pass, certify, mark the module `COMPLETE`, and begin the next module under WIP=1; no post-closure polish.

**Cross-agent handoff loops.** For MOD-001 through MOD-074, the existing guarded Claude-operation history records orchestrator/Claude handoff source and destination, bounded operation/sub-step, effective request and next-action hashes, strategy, result hash, and durable progress. Repeating an effective request or next action without progress, receiving equivalent no-progress results, or attempting a fourth same-sub-step handoff without progress raises `HANDOFF_LOOP_RISK` independently of the operation-level loop label. Do not send an equivalent request again: preserve work and require a materially different legal strategy. Two failed changed-strategy handoffs are `HANDOFF_STAGNANT`; equivalent further dispatch is prohibited. If no distinct legal path exists, mark the operation blocked or stagnant under the existing owner-stop rules. A progressing multi-step handoff is not a loop.
