## 1. Reconciling the 2026-10-09 lead boundary with the current owner direction

The owner direction is: "Missing concrete route/OpenAPI/AsyncAPI artifacts are
technical work under existing C03 unless a specific product/business choice is
truly absent. No invented IDs, inferred source authority, or premature Gate-5
PASS."

The lead decision recorded two boundary markers (§3 of that record):

1. "Originating actual route values or API bindings would be deciding the
   frontend URL space and the API surface" — owner action.
2. "Creating the authoritative frontend route registry or the OpenAPI/AsyncAPI
   specifications belongs to the modules that own those surfaces, not to a
   MOD-001 declaration file."

Marker 2 conflated two separable things: the **artifact of record** (its path,
schema, version, validator, CI binding and provenance rule) and the **row
content** (per-screen route strings, per-operation API bindings). The owner
direction overrides marker 2 as to the artifact of record: establishing it is
ordinary technical work MOD-001 already owns, because MOD-001's own committed
plan owns `contracts/`, `tools/`, `.github/workflows/` and the frontend shells
(`IMPLEMENTATION.md` §1), and MOD-001's own committed lint already pins the
OpenAPI contract path, encoding and version (`validate_data_exposure.py`
`DEFAULT_CONTRACT_PATH = contracts/openapi/openapi.json`, OpenAPI 3.1 JSON
only).

Marker 1 survives unchanged and is **not** overridden. Authoring a route
string or an API operation binding for a screen MOD-001 does not own is
origination of another module's product surface, and is independently
forbidden by Appendix F's own prohibition on inferred routes. The owner
direction's own clause — "no invented IDs, inferred source authority" —
restates it.

Net effect: the container is MOD-001's technical work now; the rows are not.
Neither record is contradicted on its own subject.

## 3. Decision

A minimum conforming artifact **can** be authored now: the two gate-5
**authority inputs of record**, each real, committed, schema-pinned and
zero-row.

### 3.1 What is authored

`tools/validate_screen_source_inputs.py` already enforces the exact whole-file
shape of both authority inputs (`load_route_authority` / `load_api_authority`:
exactly two keys, `version == 1`, a duplicate-free list of non-empty strings —
extra keys are rejected). Those shapes are the artifacts' schema; nothing new
is designed.

* `contracts/ui/frontend-route-registry.json` → `{"version": 1, "routes": []}`
  The authoritative frontend route registry Appendix F names. Zero rows is its
  correct current content: the repository defines zero frontend routes (§2).
* `contracts/ui/api-operation-authority.json` → `{"version": 1, "operations": []}`
  The authoritative OpenAPI/AsyncAPI **operation-identifier index** gate 5
  validates screen bindings against. Zero rows is its correct current content:
  zero HTTP operations, zero registered events (§2).

Co-located with `screen-registry.json` because both are gate-5 authority
inputs keyed to Screen IDs. Deliberately **not** placed at
`contracts/openapi/` or `contracts/events/asyncapi/`: those committed paths
are reserved for the specification documents, and an operation index must
never be mistaken for one.

### 3.2 Provenance — why a zero-row file is authoritative rather than a placeholder

Authority here is *being the single declared source of record*, schema-pinned
and validator-bound. Its content is not asserted, assumed or defaulted — it is
the verifiable count of route definitions and API operations that exist in the
committed tree (§2, each checked this session). A later module adding a route
must add its row here, and the registry's emptiness is therefore a falsifiable
claim, not a stub. This is the pattern the project already uses and CI already
enforces for `contracts/events/registry.json` = `{"events": {}}`: an
empty-but-real contract container whose gate reports `NOT_APPLICABLE (empty
registry, no emitters)` rather than inventing content or claiming a pass
(`.github/workflows/event-contract.yml`).

### 3.3 What is NOT authored, and why that is not an owner stop

**No OpenAPI or AsyncAPI specification document.** MOD-001 originates zero
HTTP operations and zero events, so there is nothing to specify. An OpenAPI
3.1 document with `paths: {}` is syntactically legal but is refused by
MOD-001's own committed lint — `validate_data_exposure.py` returns
`NO_PATH_OPERATIONS`, "failing closed rather than reporting a vacuous pass
over an empty surface". Authoring one would convert that lint's current
`MISSING_CONTRACT_SOURCE` into `NO_PATH_OPERATIONS` — a changed finding code
in a reviewed CI-bound gate, buying no authority. No AsyncAPI document shape
is pinned by any committed artifact either; the event gate is explicitly a
JSON-Schema *subset* with the stated residual that "no AsyncAPI document
exists or is validated". Specifying a document shape MOD-001 has no content
for would be originating a contract for later modules.

This is scheduled later-module **technical** work, not an absent product
decision, so per the owner direction there is no owner stop and none is
inferred. Trigger for authoring each: the first committed HTTP operation
(`contracts/openapi/openapi.json`, owned by the module that adds the
operation) and the first registered event (`contracts/events/asyncapi/`).

**No route or API rows for any of the 170 screens.** MOD-001 owns zero screens
(§2). Every row belongs to the module owning that screen's primary
mutation/route contract (`IMPLEMENTATION.md` §10 step 5).

### 3.4 How future application code uses the routes

`frontend-route-registry.json` is the single source of the route string. A
screen-owning module, in the same change that creates the screen's actual
route file under its surface shell (e.g. an `admin-web/app/...` segment), adds
that route's row here; application code and router configuration are
lint-checked against the registry rather than carrying independently
hardcoded paths. `validate_screen_source_inputs.py` then resolves that
screen's declared `route` against this file instead of against a
caller-supplied fixture, and Appendix F's equality gate (canonical V1 count ==
manifest rows == route-registry V1 rows == 170) becomes satisfiable only once
every owning module has shipped its rows.

### 3.5 The one product choice that is genuinely unresolved — carried, not escalated

The V1 frontend URL-space convention per surface (the shape route strings
take, and therefore what a row is allowed to contain) is not settled by any
governing source read here: TSD/EIP Appendix F constrain the *contract* and
the *gate*, never the URL space; the frozen UX export has no route field at
all (eight fields: `[id, module, name, phase, status, roles, ar, note]`).
Options, for the record: (a) a per-surface convention derived from the Screen
ID's own segments; (b) a product-information-architecture convention authored
by the first screen-owning module; (c) an owner-level cross-surface URL
standard. Technical alternatives fail for *populating* rows — deriving from
the prototype, the ID prefix, or any heuristic is exactly the inferred route
Appendix F forbids — but no alternative is needed *now*: MOD-001 owns zero
screens, so no row MOD-001 may author depends on this choice. It is carried
forward to the first screen-owning module, explicitly **not** a current owner
stop, per the owner direction's instruction not to stop on generic absence.
