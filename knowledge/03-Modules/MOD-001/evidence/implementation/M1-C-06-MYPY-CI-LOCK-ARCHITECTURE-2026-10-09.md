# M1-C-06 — minimum governed Linux x86-64 / CPython 3.13 mypy lock and install path

Status: **DECISION RECORDED; no code, lock, workflow, capability registry,
manifest, scenario disposition, review entitlement or plan-operation change.**
Sole Veyro lease, operation M1-C-06, execution role `ARCHITECTURE_CRITICAL`.
Four governing baseline hashes re-verified this turn (`verify_baselines.py`,
4/4 MATCH). Nothing was downloaded, installed, imported or executed; no mypy
run of any kind occurred; no reviewer was dispatched and no remote was mutated.

This is an architecture decision about artifact shape and fail-closed
properties. It is **not** a CAPABILITY_POLICY stage-4 independent evaluation,
not a stage-5 qualification, not a security review, and not an authorization
to rely on CAP-012. See §8.

## 1. Decision

Close the `M1-C-06-MYPY-LOCK-PLATFORM-RECONCILIATION-2026-10-09.md` gap with a
**second, additive, stage-scoped lock file** —

    backend/requirements-typecheck-linux-x86_64-cp313.lock.txt

— generated by the **unchanged** `tools/generate_requirements_lock.py` from a
fresh owner-run `pip download` directory containing the real Linux x86-64 /
cp313 wheel **bytes**, and installed on CI by

    pip install --require-hashes --only-binary=:all: --no-deps \
        -r backend/requirements-typecheck-linux-x86_64-cp313.lock.txt

into a virtual environment created by an **asserted** CPython 3.13 x86-64
interpreter on `runs-on: ubuntu-24.04`, in a job carrying no `uses:` action
reference, no `secrets.*` reference, and no required-status-check claim.

`backend/requirements-dev.lock.txt` is **not** touched, not renamed, not
regenerated and not re-headed. Its macOS/cp314 hashes, its generator-written
provenance header, and the `CAP-010`/`CAP-011`/`CAP-012` registry citations
that reference it by line number all stand unchanged. The two locks coexist;
nothing reads both.

The decision is deliberately **narrower than GOV-01-R04's type-check stage**.
It settles the *lock and install path* (how a hash-enforced mypy arrives on a
pinned Linux interpreter). It does **not** settle the *target scope* (what mypy
is then pointed at), which §6 shows is a materially larger and still-open
question. Layer 1 alone does not close GOV-01-R04.

## 2. Why a separate lock from real wheel bytes is sufficient, and why it is the minimum

The existing generator is already platform-agnostic by construction, and this
is the load-bearing observation. It derives every name and version from a real
wheel's own PEP 427/600 filename and every hash via `hashlib.sha256` over the
real file bytes (`tools/generate_requirements_lock.py` lines 47-84). It has no
concept of a platform, so it neither needs nor benefits from one: point it at a
directory of Linux wheels and it emits a Linux lock by exactly the same code
path that emitted the macOS one. Its duplicate-package guard (`scan_wheels`,
`_parse_lock`) is scoped to a single directory and a single lock file, so two
locks generated from two directories cannot collide or shadow each other.

`backend/requirements-dev.txt`'s own reviewed header already states this route
as project intent rather than as a new idea: the generated lock "is specific to
the exact OS/architecture/Python build it was generated on... not portable to a
different platform or Python minor version without regenerating." Regenerating
per platform is the sanctioned path; this decision applies it, it does not
invent it.

**Scope the lock to the type-check stage's own install set, not to all 14
dev packages.** `M1-C-06-TRUSTED-CI-ROUTING-DECISION-2026-10-09.md` §6
(Dependency A) names the broader absence — a Linux hash-locked requirements
file for the whole dev closure, needed before an integration stage can import
`psycopg`. A single all-tools Linux lock would serve both needs from one
download, and that convenience is real. It is nonetheless rejected: because
`--require-hashes` installs the entire file, one shared lock would force the
type-check venv to materialize `ruff` and `psycopg-binary` as well, enlarging
the executable surface present during a type-check run for no type-checking
benefit, and importing provenance obligations that belong to CAP-008/CAP-010's
own pending independent determinations. That cuts against `iac.md` control 2's
least-privilege standard and against CAPABILITY_POLICY's "No capability may be
granted broader scope... than the specific gap requires." The convention this
decision sets instead: **one lock per CI-stage install set, named by stage plus
platform plus ABI**, each generated by the same unchanged generator. The
disclosed cost is lock proliferation and version-drift between locks; the
mitigation is that every lock's versions are derived from the same
`backend/pyproject.toml` / `requirements-dev.txt` intent, so drift is
mechanically detectable by comparing `name==version` sets.

This explicitly does **not** close §6 Dependency A. SCN-031 remains blocked for
the reasons that decision records.

## 3. Wheel selection, download, and the independent check

> **SUPERSEDED IN PART — 2026-10-09, see §11.** The "owner-run, outside the
> agent guard" attribution in the paragraph immediately below rests on a
> premise that was already stale when this record was written: both texts it
> cites predate CAP-007's retirement. The sole agent under this lease may
> perform the acquisition and generator steps of this section in-session. The
> *technical* content of §3 — fresh empty directories, observed-not-predicted
> selection, closure comparison, two independent acquisitions, PyPI digests as
> corroboration only — is **unchanged and still binding**.

All of this is **owner-run, outside the agent guard**, exactly as
`tools/generate_requirements_lock.py`'s own docstring and
`requirements-dev.txt`'s command sequence already require. No agent session
downloads, installs or executes any of it.

Cross-platform download works from the owner's existing macOS machine — no
Linux host is required — because `pip download` selects by explicit target
tags rather than by the running interpreter:

    pip download --only-binary=:all: \
        --platform manylinux_2_28_x86_64 \
        --python-version 3.13 --implementation cp --abi cp313 \
        --dest <FRESH EMPTY DIR> mypy==2.3.1

Four properties make this governed rather than merely convenient.

**The directory must be fresh and empty.** The generator's duplicate-package
guard and its "every wheel appears exactly once" check both assume directory
purity; a reused directory silently blends platforms. A fresh directory per
download also matches the untrusted-download hygiene this environment requires.

**Selection is observed, never predicted.** pip's tag-preference ordering is
not something this decision asserts. The materialized filenames are read back
and compared to the three candidates the reconciliation record already
enumerated — `mypy-2.3.1-cp313-cp313-manylinux2014_x86_64.manylinux_2_17_x86_64.manylinux_2_28_x86_64.whl`,
`ast_serialize-0.11.2-cp39-abi3-manylinux_2_17_x86_64.manylinux2014_x86_64.whl`,
`librt-0.15.0-cp313-cp313-manylinux2014_x86_64.manylinux_2_17_x86_64.manylinux_2_28_x86_64.whl`
— plus the three platform-independent wheels. A mismatch is a stop-and-record
condition, not something to accept because the install later happens to work.
(The compressed tag sets mean `manylinux_2_17_x86_64`, `manylinux2014_x86_64`
and `manylinux_2_28_x86_64` all resolve to the same two files, which removes
most of the fragility in the `--platform` choice but does not remove the duty
to check.)

**The closure is discovered, then compared.** The command above resolves
`mypy`'s dependencies rather than passing `--no-deps`, precisely so that a
3.13/Linux environment-marker difference cannot hide a seventh package. The
resolved name set must equal exactly the six already on record (`mypy`,
`ast-serialize`, `librt`, `mypy-extensions`, `pathspec`, `typing-extensions`).
Any divergence — extra package, missing package, different version — stops the
substep and returns here, rather than being locked in.

**The check is a second independent download, not a re-read.** The generator's
docstring claims `generate` and `check` are independent code paths over the
same directory; that is true but weak. The governed sequence is therefore
`generate` against directory A, then `check` against a **separately
re-downloaded directory B**. Byte-identical results across two independent
acquisitions prove the selection is reproducible, not merely internally
consistent, and it costs one extra command.

**PyPI digests corroborate; they never generate.** The reconciliation record's
published SHA-256 values are compared against the generated lock mechanically
(`sha256sum *.whl` redirected to a committed manifest, then diffed). They are a
third independent agreement between PyPI metadata and local bytes. Per the
reconciliation record's own instruction, no PyPI hash is ever transcribed into
a governed lock — metadata is a check input, never a generation input.

Because the generator writes no filename or platform tag into the lock, the
`sha256sum` manifest is what binds each pinned hash to a named Linux wheel for
a future reviewer. It is produced mechanically, so it introduces no hand
transcription.

## 4. CI interpreter and platform pinning

**`runs-on: ubuntu-24.04`** — the exact image label, never `ubuntu-latest`. A
floating runner label carries the same reviewability objection `iac.md` control
5 raises against a floating action tag, and the three already-reviewed trusted
workflows (`scn020-trusted-event-contract.yml`, `workflow-trust.yml`,
`domain-uniqueness.yml`) already use the exact label for this reason.

**No `uses:` line anywhere.** `actions/setup-python` is unavailable, and not as
a stylistic preference: `iac.md` control 5 holds every action, including
`actions/*`, to CAPABILITY_POLICY's full 9-stage lifecycle with no
publisher carve-out, and no GitHub Action holds an `APPROVED CAP-<NNN>` row
today. `event-contract.yml` fails that control on both legs (floating
`actions/checkout@v4` and `actions/setup-python@v5`) and must not be copied —
the same conclusion the sibling routing decision reached independently.

**The interpreter is asserted, never assumed.** Mirroring
`workflow-trust.yml`'s deny-on-wrong-interpreter pattern but tightened from a
lower bound to an exact match, the stage must deny unless all of the following
hold for the interpreter it is about to use: `sys.implementation.name ==
"cpython"`; `sys.version_info[:2] == (3, 13)`; `sysconfig.get_platform()`
begins `linux-x86_64`; and `sys.maxsize > 2**32`. The exact resolved
interpreter path and full `sys.version` are recorded — this is the
"CI-interpreter evidence" CAP-012's registry row names as a remaining
dependency, and it is the artifact that finally fixes the interpreter the
reconciliation record found unfixed.

**Why 3.13 rather than the locally installed 3.14.** `backend/pyproject.toml`
sets `requires-python = ">=3.13"` and `[tool.mypy] python_version = "3.13"`,
while CAP-012's synthetic drill ran on macOS CPython 3.14.5 analysing *as*
3.13. Pinning CI to 3.13 makes the running interpreter and the analysis target
agree and puts CI at the declared floor of the supported range, removing a
variable the drill left open. The cost is a deliberate CI/local interpreter
divergence (CI 3.13 / local 3.14), which is why the two locks differ on both
platform and ABI; see §7.

**No fallback.** If no CPython 3.13 interpreter can be resolved on the runner,
the stage denies. It must not fall back to the image's default `python3`, must
not `apt install`, must not add `setup-python`, and must not proceed with a
different ABI against cp313-pinned hashes.

**Install-time controls, each closing a specific fail-open.**
`--require-hashes` is the primary enforcement: a platform-mismatched artifact
cannot be installed under it, which is what converts the macOS/Linux split from
a silent wrong-bytes risk into a loud failure. `--only-binary=:all:` removes
the source-distribution path entirely, so no build-backend code can execute —
the same reasoning `requirements-dev.txt`'s header already gives. `--no-deps`
keeps the installed set exactly the six pinned digests, with no unpinned
transitive arrival. `--index-url https://pypi.org/simple` plus
`PIP_CONFIG_FILE=/dev/null` and a cleared `PIP_*` environment prevent an
ambient config or environment variable from redirecting the index, which would
otherwise defeat the whole chain; `--no-cache-dir`, `--no-input` and
`--disable-pip-version-check` keep the step deterministic and side-effect-free.
Per `requirements-dev.txt`'s own convention, the venv's ensurepip-bundled pip
is used **as-is** — no `pip install --upgrade pip`. Its version is recorded.

**Network egress is a new property and is named as such.** Unlike the SCN-030
drill route, which has zero egress, this stage contacts PyPI over HTTPS. The
governed boundary is that the set of bytes able to enter the job is exactly the
six pinned digests, enforced by `--require-hashes` plus `--only-binary=:all:`
plus `--no-deps`.

**Route and authority are inherited, not re-decided.**
`M1-C-06-TRUSTED-CI-ROUTING-DECISION-2026-10-09.md` already settled this: a
`pull_request`-triggered zero-authority job with `permissions: {}`, no
`secrets.*`, no `uses:`, explicitly **not** claimed as a required status check,
whose evidential value is the inspected run rather than the check conclusion.
Its §7 first constraint binds here verbatim — a drill-route run may evidence
that the install *works*, and may never be presented as GOV-01-R04's
non-bypassable-gate criterion. Blocking-gate status remains a separate
enforcement problem behind the trusted-anchor route, branch protection, and the
still-open same-name-spoof negative (C2/N5). Live execution also still needs a
disposable same-repository branch and PR, which the SCN-020-scoped live
authorization does not cover — a named technical/authority dependency, not an
inferred owner stop.

## 5. No generator change is mandatory

`tools/generate_requirements_lock.py` is **not** modified, and this is a
positive finding rather than a deferral.

Correctness does not require it: the generator is platform-blind, its guards
are per-directory, and the fail-closed property at the only moment it matters
comes from pip's `--require-hashes` at install time, not from anything the lock
file could say about itself. A platform-mislabelled lock cannot install the
wrong bytes; it can only fail.

The one genuine shortfall is legibility, not safety — the lock records
name/version/hash but not the wheel filename or platform tags, so a reviewer
cannot tell from the lock bytes alone which platform they describe. That is
addressed at zero risk by the committed `sha256sum` manifest of §3 plus the
platform-and-ABI-bearing filename, both mechanically produced.

Against that, editing the generator would re-open the review surface of a tool
with existing independent-review history (BUG-036 Rounds 3-5) that every
current lock's provenance depends on, in exchange for no correctness gain. The
minimum governed path therefore leaves it untouched. A future multi-platform
generator extension remains a legitimate option; it is simply not a dependency
of this work, which is the same conclusion the reconciliation record reached.

## 6. The target-scope problem this decision deliberately does not solve

An inspection of `backend/app` this turn surfaces a material constraint that
the lock/install path alone does not address, and it would be dishonest to
record Layer 1 as if it closed the stage.

`backend/app` (23 `.py` files) imports `psycopg`, `psycopg.rows`, `pytest`, and
— from `backend/app/modules/conftest.py` — `tests.harness.postgres` and
`tests.harness.tenant_context`. Three consequences follow.

First, the install set required to type-check real `backend/app` under
`strict` is strictly larger than mypy's own six-package closure, because
unresolved imports are errors when `--ignore-missing-imports` is off. Second,
`strict` follow-imports reaches **outside** CAP-012's declared target: its
registry row scopes it to "`backend/app` only" and lists `backend/tests` under
"Not covered, no reliance of any kind," yet `tests.harness.postgres` is
reachable from `backend/app`'s own import graph. Third, a plausible
minimization exists but is unverified — type resolution needs only `psycopg`'s
typed pure-Python distribution, not the compiled `psycopg-binary`, so the
additional install set may be platform-independent after all. Whether
`psycopg==3.3.6`'s existing lock hash names a `py3-none-any` wheel was **not**
checked by the reconciliation record, which covered only the six mypy pins.

These are CAP-012 scope questions with a lock/install consequence, not lock
questions. They belong to CAP-012's pending independent determination and to a
separate decision, and they are listed in §7 as material unknowns. Layer 1 is
sufficient to install a hash-enforced mypy on a pinned Linux interpreter and to
run a synthetic-fixture drill; it is **not** sufficient to type-check real
Veyro code, and no later record may treat it as such.

## 7. Material unknowns

1. **Does `ubuntu-24.04` reliably provide a CPython 3.13 x86-64 interpreter
   without an action?** The runner image's tool cache is the only candidate
   source given §4's no-`uses:` constraint, and its contents are not a
   contractual interface; `/usr/bin/python3.13` is a second candidate and is
   equally unverified. Neither may be assumed. If neither resolves, the stage
   denies and the question returns here — the fallbacks (an `actions/setup-python`
   reference pinned to a 40-hex SHA, or a digest-pinned `container:` image) are
   each a new third-party-executable capability review surface under `iac.md`
   control 5, and **neither is adopted or pre-authorized by this decision.**
   This is the single unknown most likely to invalidate §4.
2. **Which exact wheels pip selects for the stated target tags.** Predicted
   from the reconciliation record's PyPI metadata, never asserted; resolved
   only by observing the download (§3).
3. **Whether the 3.13/Linux closure is exactly the six packages on record.**
   Environment markers can differ from the macOS/3.14 resolve.
4. **Whether `psycopg==3.3.6`'s existing lock hash names a platform-independent
   wheel**, and relatedly whether `pytest`'s does (CAP-011 records it as
   `pytest-9.1.1-py3-none-any.whl`, matched to PyPI). Determines whether §6's
   additional install set needs its own Linux pins at all.
5. **Whether `mypy-2.3.1-py3-none-any.whl` can replace the compiled wheel.**
   PyPI publishes it, but `librt` and `ast-serialize` have no universal wheel,
   so whether the universal mypy still requires them (and at what performance
   cost) is unknown. The decision deliberately does not depend on resolving it.
6. **The CI 3.13 / local 3.14 interpreter divergence.** Justified in §4, but
   whether the project should instead converge both on one minor version is a
   standing question, not something this decision forecloses.
7. **CAP-012's target scope under follow-imports** (§6), including whether a
   GOV-01-R04 type-check of `backend/app` can be meaningfully bounded to
   `backend/app` at all.

## 8. Architecture decision versus capability review authorization

These are different acts by different roles and must not be conflated.

This record is the former. It fixes artifact shape, platform pinning, and
fail-closed properties. It creates no entitlement to run anything.

It is **not** the latter. CAPABILITY_POLICY stage 4 requires an independent
Opus `veyro-security-reviewer` determination, reviewing evidence it did not
itself produce, before `review_status` may read `APPROVED`; its model-routing
clause is explicit that a `qualified_by` naming only a Sonnet tier with no Opus
`approved_by` leaves a capability at `QUALIFIED`. This worker authored the
architecture, and is therefore structurally disqualified from being that
reviewer for this path.

CAP-012 accordingly remains **QUALIFIED — NOT APPROVED**, `lifecycle_status`
not ACTIVE, with no reliance of any kind permitted. `validate_capabilities.py`
is expected to continue reporting `CAPABILITY_NOT_APPROVED`; that is the
intended fail-closed hold, not a defect to route around.

**How the ordering keeps an unapproved CAP-012 away from real Veyro code.**
CAPABILITY_POLICY stage 5 permits touching an unregistered or unqualified
capability only in a qualification drill, and only against synthetic fixtures.
The install path is therefore sequenced so that the first execution of the
Linux-installed mypy targets a synthetic fixture the job itself creates — never
`backend/app`, `backend/tests`, `backend/migrations`, `tools/**`, or any other
Veyro path, and never a committed `.mypy_cache`. Pointing the stage at real
code is a distinct, post-APPROVED change requiring the §6 scope question to be
settled first. The real-code invocation is therefore **not authored at all** at
this stage, rather than authored and disabled.

**12.1 — SUPERSEDED: §3's compressed-tag interchangeability sentence.** §3's
parenthetical "(The compressed tag sets mean `manylinux_2_17_x86_64`,
`manylinux2014_x86_64` and `manylinux_2_28_x86_64` all resolve to the same two
files, which removes most of the fragility in the `--platform` choice…)" is
**withdrawn as factually wrong**. It holds for `mypy` and `librt`, whose
wheels carry all three tags, and is false for `ast-serialize`, which publishes

performs no backward expansion of a PEP 600 `manylinux_x_y_arch` string
(`pip/_internal/utils/compatibility_tags.py::_get_custom_platforms`), so
`--platform` is a literal tag-set membership test, not a glibc floor. The
`--platform` choice is exactly where the fragility lives. §3's adjacent
