## 2. Route chosen, and why it is the smallest sound one

**Pin: the Linux CI lock is authoritative; it was not edited.** The
alternative — downgrading the CI lock's `iniconfig` to 2.3.1 → 2.3.0 so one
closure covers both locks — was rejected. That lock's own header records that
it was generated by `tools/generate_requirements_lock.py` from real downloaded
wheels; hand-editing one pin to 2.3.0 would falsify that provenance claim, and
§5's control shows the change buys no behavioural difference. The two locks
simply resolved at different times (`iniconfig 2.3.1` was published
2026-10-06), and iniconfig is the only closure member that differs. So the
registry row was corrected to name the artifact set CI really installs, and to
state the dev-lock/`backend/.venv` divergence explicitly rather than describe
one closure as if it were the only one.

**Scope: extend the drafted scope to the one extra file; do not narrow the
candidates.** The alternative — deleting the `idempotency-contract` suite from
the runner and the workflow so the drafted `backend/tests`-only scope became
true — was rejected: it would remove a real GOV-01-R02 control
(SCN-MOD001-016(a)'s focused tests) to make a draft registry sentence correct,
and this operation was charged with preserving the candidates. The row now
names the closed five-entry allowlist that the runner's own literal table
already is.

Net effect: both inconsistencies resolved registry-side. **No CI artifact
correction turned out to be essential**, so neither the lock, the workflow nor
the runner was modified (§7 pins all three as unchanged).

## 5. What the iniconfig divergence actually costs

A substitution control held pytest at the pinned 9.1.1 and swapped only
`iniconfig 2.3.1 → 2.3.0` (the dev-lock pin, installed from its official
verified wheel). Both the extra target and `backend-unit` ran rc 0 with an
identical pytest banner (`platform darwin -- Python 3.13.13, pytest-9.1.1,
pluggy-1.6.0`), identical `configfile`/`rootdir` resolution, and identical
outcomes. So the divergence is **not behaviour-affecting for the drilled
cases** — which is the honest basis for recording it rather than forcing one
of the two locks to move.

That same control exposes a real residual, recorded in the registry row: the
runner's version probe pins **pytest alone**. A closure member drifting
(iniconfig included) is caught only by the hash-enforced install in CI, never
at invocation time. Nothing in this operation changed that, and widening the
probe would be a scope change for a later qualified decision, not a
reconciliation.
