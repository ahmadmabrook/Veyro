NAMING RULES

HIERARCHY RULE
One primary per view. Not per card, per view. A screen with two primaries has an unresolved information hierarchy, and design review rejects it rather than restyling it. Destructive is never adjacent to primary — it lives behind an actions menu or at the opposite end of the container.
CONTENT
Verb first, object second, no gerunds: “Renew membership”, never “Membership renewal”. Amounts belong in destructive and financial labels — “Refund JOD 28.00” — so the confirm reads the consequence.

All share one shell — label, control, description, message, prefix, suffix, contextual action — so a new field type is a control swap, not a new component. Message slot holds exactly one message at a time, priority error > warning > success > description.
FORM RULES · §24
Pre-fill from the record, always — the nutrition builder asks two unknowns, not twelve knowns. Autosave with a visible “saved” marker on long forms; explicit save only where a set of changes must commit together. Validate on blur, never on keystroke; re-validate on submit. Required is marked, optional is not — whichever is rarer gets the mark. Financial forms state the consequence above the submit, not in a dialog after it.

Date & time

الأسبوع يبدأ السبت. الأيام تتقدم من اليمين لليسار، والأسابيع تنزل للأسفل. أسماء الأيام كاملة وليست مقطوعة.
THE FIVE RTL DECISIONS HERE
1 · Days mirror, weeks do not. Columns run right-to-left; rows still descend. Flipping both is the classic bug and produces a calendar that reads bottom-up.

2 · Chevrons mirror, and so does their meaning. Previous sits on the right in RTL. The icon flips and the position flips — doing only one inverts navigation.

3 · Week start is a market token, not a locale guess. Jordan is Saturday; the same Arabic tenant in another market may differ.

4 · Range fields keep reading order. “From” stays first in the tab and reading order; only the box positions mirror. Swapping them is how a user books a range backwards.

5 · Numerals follow the tenant setting — Arabic-Indic here — and the grid width is set from the widest numeral form, so switching numerals never reflows the calendar.
AND THE CONSEQUENCE NOBODY PLANS FOR
The Arabic calendar is wider than the Latin one — 352px against 286px — and the two headers are different heights. That asymmetry is correct, not a bug to squeeze away. Foundations sets a hard 13px floor for Arabic, so the 9.5px mono day names the Latin grid uses legitimately have no Arabic equivalent; and full day nouns (الاثنين، الثلاثاء، الأربعاء) are the only honest short form — اثن and ثلا are mid-word cuts, not abbreviations any reader recognises. Arabic needs the room, so the component takes it. Any layout placing a calendar in a fixed 286px slot is wrong in Arabic and has to be sized from the Arabic build, which is the “containers sized for Arabic” rule doing actual work rather than being restated.

TIME & WEEK VIEW
TimePicker is a stepped list at the tenant's booking granularity (15 min at Nadi Group), never a free text field — a class cannot start at 19:07. WeekView is the scheduling surface: time on the vertical axis in both directions, resources as columns, drag to move with a confirm on conflict. DayView is WeekView at one column and is the Front Desk default.
All six components take timezone, weekStart and numerals from tenant policy, never from the browser. A member in Dubai booking a Khalda class sees Amman time labelled as Amman time.
KEYBOARD & NARRATION
Calendar is one tab stop. ←→ day, ↑↓ week, PgUp/PgDn month, Home/End week bounds, ⏎ select, Esc close without selecting. In RTL, ← moves forward in time — arrow keys follow visual direction, not calendar direction, because the hand follows the eye.
Announced as “Wednesday 19 August 2026, today, available” — weekday, date, relation, availability. Unavailable dates state why: “fully booked” rather than just “disabled”.
06 · §30 · RESOLVES THE STEP 1 SEVERITY FLAG

Status and severity

One four-step severity scale consumed by both the badge and the row edge-mark. The edge-mark carries the row-level roll-up; the badge always names the specific state. They are the same scale expressed at two granularities, which is what stopped them reading as two independent signals.

SEVERITY · 4 STEPS
neutralA fact. Active, Paid, Confirmed, On plan.
infoWorth knowing, no action. Trial, Pending sync, Waitlisted.
attentionNeeds a human soon. Expiring, At risk, Frozen, Approval pending.
criticalBlocking or losing money. Overdue, Failed, Denied, Expired.
Four steps, not five — “success” is not a severity, it is the neutral case. A green badge on every paid invoice makes a table of paid invoices look like a celebration and makes the one unpaid row harder to find.
DOMAIN VOCABULARIES · FIXED
Membership Active · Trial · Frozen · Expiring · Expired · Cancelled
Payment Paid · Pending · Failed · Refunded · Partially refunded
Booking Confirmed · Waitlisted · Cancelled · No-show
Access Granted · Denied · Restricted
These strings are the vocabulary from the Foundation terminology system, not new copy. A status the vocabulary does not contain cannot be rendered — the component takes an enum, not a string, so an engineer cannot invent “Semi-active”.
Never colour alone. Every badge carries its label; icon-only status is a defect at any density.

COMMAND PALETTE · FOUR RESULT CLASSES
Always in this order: Ask Veyro (natural-language question) · Records · Actions · Go to. Grouping is fixed so muscle memory survives — a result never changes class between sessions.
Actions never execute on ⏎. They open a preview stating target, effect and required approval — the P1-4 taxonomy applied. Destructive and financial actions are excluded from the palette entirely; they are reachable only from the record they affect, because a fuzzy match should never be able to refund someone.
Every result is post-filtered by permission and tenant. A result a user cannot open does not appear — search is never a route around authorization.
FILTERS · ONE UX EVERYWHERE
Quick chips for the two or three filters that matter per surface; “＋ Filter” for everything else; applied filters always render as removable chips with a count and a Clear all. Saved views are filters plus columns plus sort, named and optionally shared. No module invents its own filter UI — that was the CX-R1 risk from the Foundation.
ADMIN NAV · 3 LAYERS RENDERED
Global chrome (scope switcher, ⌘K, tasks, alerts, account) · rail of eight composed from role and scope, with an “All areas” directory · secondary nav capped at seven. The rail is generated, never a static tree with disabled rows — a receptionist and an accountant get different rails, not the same rail greyed differently.
SCOPE SWITCHER AT CHAIN SCALE
Searchable, grouped by brand then region, recents first, multi-select for comparison. Never a dropdown — a 50-item list is a search problem. Current scope is always visible in the chrome, because “which club am I looking at” must never require a click to answer.
MOBILE NAV
Coach: four tabs plus a create action. Member: five tabs. Both bottom-anchored with 44px targets, labels always visible — icon-only tabs fail both accessibility and Arabic, where the label is the disambiguator. Front Desk uses mode tabs, not a rail.
