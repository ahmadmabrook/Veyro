04 · CARRIED FORWARD

Four items that are not closed, and why that is correct

VALIDATE-1 · A11Y IS SPECIFIED, NOT TESTED
Every contract is written; none has met a screen reader, because no build exists. One session with a real NVDA or VoiceOver user on the attention queue, POS checkout and set logger, in Phase 8. Booked as a task, not claimed as a pass — six precision defects in this project were caught only by measurement, and this is the same class of risk.
POLICY-1 · NUTRITION CLINICAL GATE
Architecturally unblocked, deliberately unanswered. The routing point and its four outcomes ship; the rules are a market-specific compliance input owned outside the product. Until a market publishes them, its tenants run review-all or nutrition-disabled. Per your instruction, Veyro invents no clinical criteria.
DS-P2-1 · QUEUED-ORDER TRAY
Surfaced by validation screen 6. The POS banner promises card orders are queued; no component shows or reconciles that queue. Composable from DataGrid plus TaskRow, so it is a specification gap rather than a structural one. Sized for Phase 8, week one.
DS-P2-2 · DEGRADED-METHOD PRECEDENCE
When one payment method fails, which becomes primary? Cash was used in screen 6, but the rule is unwritten and a cashless tenant needs a different answer. A tenant-configurable ordered fallback list, specified alongside DS-P2-1.
Ten further P2/P3 items from the Phase 6 review remain open and unchanged: table column presets per role, saved-view sharing permissions, notification digest grouping, lead-source attribution display, class waitlist promotion copy, coach qualification badges, document expiry reminders, member referral surface, staff shift handover notes, and export column selection. None blocks hi-fi; each is a screen-level decision Phase 8 makes in context rather than a system-level gap.

WHY THIS BELONGS IN THE AUDIT
Eight contrast, arithmetic and precision defects, four of them inside the mechanisms built to prevent that exact class — including one in a document certifying accessibility, one in the Arabic demo built to prove Arabic was handled, and two in this audit — the document whose §05 is this list. Each was caught by external review, not by me re-reading my own work.
The conclusion is not that the system is unsound — the defects were in documents about the system, and each fix held. It is that my adherence is not a control. Which is why §07's contrast matrix and the three CI gates are shipped artefacts rather than principles, and why VALIDATE-1 is a booked session rather than a checkbox. A design system whose author has demonstrated this failure rate should be trusted exactly as far as its automated checks reach.
06 · GOVERNANCE · §76–§80

How v1 survives contact with Phase 8

CONTRIBUTION
A new component requires: three real use sites, a state matrix, all four contracts, and a documented reason no existing family covers it. Visual variation is never a new component. Rejections are recorded with their reasoning so the same proposal is not re-litigated.
THE THREE CI GATES
A merge blocks on: a component referencing a Layer 1 primitive; a text/surface pairing absent from the contrast matrix or below threshold; a spacing or radius value outside the scale. All three encode failures this project made by hand.
VERSIONING
Semantic. A token rename or a state removal is major; a new variant is minor. Deprecation runs two minor versions with a codemod where mechanical. White-label token contracts are frozen at v1 — they are a published customer promise, not internal API.
DESIGN QA IN PHASE 8
Every screen ships against a checklist: tokens only, states complete, both directions rendered, four contracts satisfied, terminology from the vocabulary, confirmation tier correct, money kinds explicit. A screen that needs an exception files a system change instead of a local override.
WHAT PHASE 8 MAY NOT CHANGE
The severity scale, the confirmation taxonomy, the permission states, money presentation, the Arabic type rules, and the white-label guardrails. These are safety and correctness decisions with review history behind them; reopening one is a documented system change, never a screen-level call.
FIRST WEEK OF PHASE 8
Specify DS-P2-1 and DS-P2-2, book the screen-reader session, generate the token JSON and the three CI gates, then build Admin Command Center and Member 360 first — the two screens that exercise the most of the system and will surface anything the six validation screens missed.
OFFICIAL VERDICT · VEYRO DESIGN SYSTEM v1
APPROVED
76 of 80 requirements complete. Zero P0, zero P1 open — all twelve closed with evidence recorded per item. The four group G requirements are specified but untested. Separately, four items are carried forward with stated reasons, none structural: one is a booked test that cannot run before a build exists, one is a clinical policy correctly owned outside the product, and two are P2 specification gaps that the validation screens surfaced precisely because screen 6 was chosen to be a failure case.
The system is approved because it holds under composition — six real screens, four densities, two directions, zero new values and zero new components — and because the places it does not yet hold are named rather than hidden. Two conditions attach: DS-P2-1 and DS-P2-2 are specified in Phase 8 week one, and the screen-reader session happens before hi-fi sign-off, not after. Neither blocks starting.
Phase 8 — full product high-fidelity UI — is unblocked. Start with Admin Command Center and Member 360, which between them exercise more of the system than the other four validation screens combined.
