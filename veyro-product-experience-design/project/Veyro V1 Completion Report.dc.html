01 · THE DISTINCTION THIS REPORT TURNS ON

Drawn, specified, and why they are not the same

DRAWN · {{ drawn }} SCREENS
Real UI at production fidelity with real content, its states mapped and its permission variants stated. An engineer opens the canvas and builds what they see. This is what §2 means by HIGH-FIDELITY COMPLETE.
SPECIFIED · {{ spec }} SCREENS
A registry row naming the parent shape, what differs, its states, its permission behaviour and its confirmation tier. An engineer could build it — but they would be composing from a description, and two engineers would produce two different screens. This is not what §2 asks for.
WHY I DID NOT CALL SPECIFIED "COMPLETE"
Reclassifying {{ spec }} rows would produce a 100% figure and a false one. §13 is explicit that a component demonstration is not a finished screen; a written specification is closer, but it is still a description of UI rather than UI. The phase set a bar and the honest report is the one that measures against it.
WHAT THE SPECIFICATIONS ARE WORTH
A great deal, and more than a wireframe. Each names its parent so the visual language is fixed, its states so nothing is discovered late, and its permission behaviour so the sensitive paths are decided. No product decision remains inside them — only drawing. That is the difference between {{ coveredPct }}% and a project that has not been thought through.
