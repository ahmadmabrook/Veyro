04 · WHAT HAPPENS NEXT

How this registry was worked through

BATCH ORDER, AS RUN
Admin first and largest — every other surface reads data shaped there — across batches A and F–L. Front Desk and POS next (B, M), small but the most operationally costly per missing screen. Then Coach (C, N), Member (D, O, P) with the most screens per feature because every flow is a drill-down, and Console last (E, Q). {{ v1Gap }} gaps remain.
HOW A GAP CLOSES
A row moves to COMPLETE when the actual screen is drawn with real content, its states mapped, its permission variants stated, and its file reference recorded here. Not when a component that could build it exists. That distinction is the whole reason this registry was built.
AR POLICY · §16
BUILT = an actual Arabic canvas exists. CONTRACT = covered by a validated RTL contract from a built screen of the same shape. NEEDS = high-risk and requires its own build. Currently {{ arBuilt }} built, {{ arNeeds }} still needing a build. No screen is marked contract-covered unless a built screen of that exact shape exists.
THE HONEST FRAMING
The gap count now reads {{ v1Gap }}, and when this phase began it read {{ moved }}. Neither number was typed — both are the length of a filtered array, which is the only reason either can be trusted after this project's seven counting defects, the last of which was this page silently rendering NaN while claiming to be canonical. The standard held throughout: a row moved to DONE only when the actual screen was drawn, never when a component that could build it existed. Some of those rows are genuinely small — a confirmation, a receipt, a settings pane — but each was a screen an engineer would otherwise have had to invent.
