# THIS FILE IS THE UNLOCKED SOURCE OF INTENT — do not install directly
# from it with plain `pip install -r`. It has no hashes and does not
# name the transitive closure, so a plain install is not byte-for-byte
# reproducible, and it does not force wheel-only acquisition (a plain
# `pip download`/`pip install` could fall back to a source distribution,
# running arbitrary build-backend code). The actual install target is
# the generated, hash-locked `backend/requirements-dev.lock.txt` (does
# not exist yet). Full corrected sequence — bare `pip` only, no
# pip-tools (see BUG-036 Round 4 for why pip-tools was evaluated and
# rejected), and no manual hash transcription (see Round 5 —
# tools/generate_requirements_lock.py derives every name/version/hash
# programmatically from the real downloaded wheels):
#
#   python3 -m venv backend/.venv          # do NOT `pip install --upgrade pip` — use the bundled version as-is
#   backend/.venv/bin/pip download --only-binary=:all: -r backend/requirements-dev.txt -d /tmp/veyro-wheels
#   backend/.venv/bin/python3 tools/generate_requirements_lock.py generate /tmp/veyro-wheels backend/requirements-dev.lock.txt
#   backend/.venv/bin/python3 tools/generate_requirements_lock.py check    /tmp/veyro-wheels backend/requirements-dev.lock.txt
#   backend/.venv/bin/pip install --require-hashes -r backend/requirements-dev.lock.txt
#
# `--only-binary=:all:` makes the download fail loudly if any package in
# the closure has no wheel for this exact machine, rather than silently
# building from source — treat that failure as a new, separate decision
# point, never as something to route around.
#
# The resulting lock file is specific to the exact OS/architecture/
# Python build it was generated on (macOS/Python-3.13-build-specific,
# not portable to a different platform or Python minor version without
# regenerating) — see BUG-036 Round 5 for the full explanation.
#
# (project-local venv only — see BUG-036 Tier 2(a) for why none of this
# ever runs through an agent's own Bash tool).
